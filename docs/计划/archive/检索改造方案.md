# 检索改造方案：短条款 + 同义不同词

> 2026-11-17。起因：条款切分后文本变短（中位 51–62 字），BM25 排序质量下降，`k=6` 捞不到对的条款、`k=12` 才捞到但模型会崩。同时六张表的 query 要跨不同招标文件复用，存在「同义不同词」的问题。
>
> 当前基线：**15/18、负例 3/3、违规 0、★2、flaky 1**（B1-a + k=8 之后）。

---

## 一、两个问题要分开看

| 问题 | 表现 | 本质 |
|---|---|---|
| **A. 短条款检索不准** | 条款中位 51–62 字，`4分`、`三日内`、`不低于3年` 这类条款字面上没有区分度 | 信号稀疏 + 缺上下文 |
| **B. 同义不同词** | 不同招标文件里「磋商保证金 / 投标担保 / 投标保证金」指同一件事 | 词汇没对齐 |

这两个问题的解法**正交**：A 靠分词粒度和上下文，B 靠词表对齐。必须分开做、分开验证——否则门禁分数变化说不清是谁的功劳。

---

## 二、别人怎么做（论文与工业实践）

### 2.1 别人也用短条款，而且是专门的研究方向

「条款级 / 条文级检索」在英文文献里叫 **provision-level**、**clause-level**，不是民科需求：

- **ACORD**（ACL 2025）：法律合同条款检索数据集，[aclanthology.org/2025.acl-long.1206.pdf](https://aclanthology.org/2025.acl-long.1206.pdf)
- **UK 法规条文检索**（Springer 2025）：[Provision-level evaluation and an open distilled model](https://link.springer.com/article/10.1007/s10506-025-09501-6)

**共同结论：没人靠调 BM25 参数解决，都是「宽召回 + 重排」。**

### 2.2 ACORD 的实测：BM25 不用换，要换后面那一层

同一份论文里的数字（NDCG@10）：

| 方案 | NDCG@10 |
|---|---|
| BM25 + GPT-4o pointwise 重排 | **79.7** |
| 微调的 cross-encoder（MiniLM） | 60.9 |
| BM25 单独 | 更低 |

原文：*"Overall, a BM25 retriever paired with pointwise GPT-4o performs best."*

**含义**：BM25 作为召回器是够用的，问题在它后面没有重排。所以不要急着换 embedding，先补重排层。

### 2.3 Anthropic 的 Contextual Retrieval：在索引时解决，不是查询时

[anthropic.com/engineering/contextual-retrieval](https://www.anthropic.com/engineering/contextual-retrieval)

做法：索引前给每个 chunk **前置一段说明**（它属于哪份文件、哪个章节、在讲什么），让 BM25 和向量都拿到原本没有的词汇。

实测（top-20 检索失败率，1 - recall@20）：

| 做法 | 失败率 | 降幅 |
|---|---|---|
| 标准 embeddings + BM25 | 5.7% | 基线 |
| + Contextual Embeddings | 3.7% | **35%** |
| + Contextual BM25 | 2.9% | **49%** |
| + 重排（150 → 20） | 1.9% | **67%** |

**对得上我们的场景**：`4分` 单独成条款，BM25 不知道它是「商务部分 / 标准分 / 分项」。Anthropic 用 LLM 写这段说明；我们已经有 `chunk_clauses` 生成的「父标题链 + 本条」context，**但 BM25 索引的是** `text`**，不是** `context`——这是白送的一步没走。

### 2.4 RRF 是混合检索的标准融合方式

[Azure AI Search 文档](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)：BM25 与向量并行跑，用 `1/(rank + 60)` 融合，`k=60` 是实验最优常数。

我们现在的做法是「BM25 取 k 条 + 向量取 k 条，**合并去重**」。区别很实际：RRF 让「两条通道都排前面」的文档得到加成，去重只是简单并集。

### 2.5 SPLADE / BGE-M3：学习式稀疏

- [SPLADE vs BM25](https://zilliz.com/learn/comparing-splade-sparse-vectors-with-bm25)：SPLADE 是「学习式稀疏」，能扩展同义词，对模糊查询更强
- [BGE-M3](https://arxiv.org/html/2402.03216v3)：一个模型同时出 dense / sparse / multi-vector

关键点：**SPLADE 的扩展发生在索引侧**（query 原样进，doc 侧生成扩展词权重），不是查询侧。

### 2.6 中文 BM25 的默认做法

不是单字切。主流是 **jieba 词 + 字 bigram 混合**：

- 词给语义单元（「投标保证金」是一个 token，不会和「履约保证金」共享三个字）
- bigram 兜住未登录词（「磋商保证金」即使词表没有，`磋商`+`商保`+`保证金` 也能部分匹配）

## 三、我们的问题诊断

### 3.1 分词粒度：单字切在短条款上先崩

`tender/index.py:_tokenize` 现在是单字切。三个后果：

1. **区分度为零**：「投标保证金」与「履约保证金」共享 `保/证/金` 三个字
2. **短文本信号更稀**：51–62 字的条款单字切完约 50 token，其中虚字（的/了/在/是）占一半，真信号可能只有 3–4 个
3. **长段落能凑合**：字多、虚字权重被稀释；条款没有这个缓冲

### 3.2 同义问题：C1 做了词表，但接错了地方

C1 建了 `ontology/terms.yaml`（20 概念 / 35 别名）和 `normalize()`，但只写了函数没接入索引。

C2 试的是 `expand_query()`，**方向错了**：

| | 做法 | query 长度 | 实测结果 |
|---|---|---|---|
| **扩展**（`expand_query`，已回滚） | query 追加所有别名 + `weak` 泛词 | 涨 3–5 倍 | 14/18 → **12/18**，flaky 1→3 |
| **归一**（应该做的） | query 和**文档**都把别名换成标准词 | **不变** | 未测 |

```
索引时：条款「磋商保证金金额 8000 元」→ normalize → 「投标保证金金额 8000 元」
查询时：query「磋商保证金」        → normalize → 「投标保证金」
```

两边都归一，BM25 自然命中，query 一个词都没多。这和 SPLADE 的思路同构（扩展在索引侧），只是我们用词表而不是模型。

### 3.3 缺重排层

现在召回 8 条直接喂给抽取模型，等于让抽取模型兼职做重排。ACORD 证明了：**召回宽一点 + 单独重排** 比「召回窄一点、模型自己挑」强。

## 四、方案（按性价比排）

| 步骤 | 改什么 | 解决哪个问题 | 改动量 | 风险 |
|---|---|---|---|---|
| **1. 索引归一** | `chunk_`* 生成 text 时过 `normalize()`；query 也过 | B 同义 | 小 | 极低 |
| **2. 分词改 jieba + bigram** | `_tokenize` | A 短条款 | 小 | 低 |
| **3. BM25 索引加 context** | `_tokenize(c["context"] + " " + c["text"])` | A 短条款 | 1 行 ×2 处 | 低 |
| **4. RRF 融合** | 合并去重 → `1/(rank+60)` | 排序质量 | ~20 行 | 低 |
| **5. LLM 重排** | 召回 20 → 重排取 8 | 排序质量 | ~30 行 + 1 次调用 | 中（慢、贵、不稳） |
| 6. BGE-M3 sparse | 换 embedding | — | 大（重建索引） | 高 |

### 为什么 1、2 先做

- **改动小、可独立回滚**：每一步都能单独跑门禁，失败就退
- 直接对症：1 解决同义，2 解决短条款
- 不依赖模型：结果可复现，符合「可判错」原则

### 为什么 5 放最后

ACORD 证明它收益最大，但代价是每轮多一次模型调用。现在一轮门禁已经 5–15 分钟，加一层重排会更慢，而且引入模型不确定性（同一题今天过明天不过，回归就废了）。

### 为什么 6 不建议现在做

换 embedding 要重跑全量索引 + 重新校准基线；而我们的 query 是**固定领域词**（"投标无效 最高限价 预算"），不是用户口语，SPLADE 的语义扩展优势用不上——反而可能把无关表拉高，`expand_query` 那次已经证明了。

## 五、实验计划（一次只改一个）

| 实验  | 改什么                                                    | 看什么指标                                    | 判定    |
| --- | ------------------------------------------------------ | ---------------------------------------- | ----- |
| E1  | 索引 + query 双向归一/Users/ning/Desktop/tender-lint/docs/计划 | 同义题（`wl-bond`、`cz-cap`）是否回来；总分是否 ≥15     | 掉分就回滚 |
| E2  | `_tokenize` 改词 + bigram                                | 短条款题（`cz-format-bid-sheet`、`bj-decrypt`） | 同上    |
| E3  | BM25 索引加 context                                       | ★ 覆盖是否保持 2；总分                            | 同上    |
| E4  | RRF 融合                                                 | 排序质量（top-3 命中率）                          | 同上    |

每个实验都要：

1. 跑 3 次取多数
2. 对比 `last.json` 基线
3. 记录「改了什么 → 分数怎么动」，写进本节

**不要一次改两个**——分数动了也说不清是谁的功劳。

## 六、已知的坑（别重复踩）

| 坑 | 现象 | 原因 |
|---|---|---|
| `expand_query` 注入检索 | 14/18 → 12/18，flaky 3 | query 长度涨 3–5 倍，BM25 打分被稀释 |
| 整组兄弟条款拼 context | 正例 15 → 10 | 单条 3000 字，k=6 合计 1.8 万字，提示词爆 |
| 扩检索到 `format` 章 | ★+1 但违规 1 | 投标书模板里的「中标后提交履约保证金」被当成废标条件 |
| query 换成纯后果词 | `bj-cap/cz-cap/wl-cap` 三题全掉 | 「报价超过最高限价的投标无效」的入口词是「最高限价」 |
