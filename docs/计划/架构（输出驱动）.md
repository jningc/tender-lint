# 架构：从输出倒推

> 2026-11-21。**取代 `检索与扫描架构.md` 的顶层判断**（那份的取数方式表仍有效，本文改的是「按什么维度组织」）。
>
> 起点不是「技术上该怎么切」，而是 `sample/输出形式-落地版.md` 那五条硬规则——它们直接决定解析必须做到什么粒度。

---

## 一、判断

**应该按文件结构设计架构，但不是从「怎么切文档」出发，是从「输出的一行长什么样」倒推。**

理由很硬：`输出形式-落地版.md` 里有三条规则，用现在的架构**根本实现不了**，不是精度不够，是语义上做不到。

---

## 二、输出形式逼出的三条硬约束

| 输出要求 | 逼出来的架构约束 | 现在 |
|---|---|---|
| **情形 = 条件句，含情态词，可展开原文整句** | 解析必须保留**句级原文 + 情态词位置** | ❌ 只有条款级 text |
| **页码带 role**（`p23 无效句`、`p8 金额`） | bbox 细到**句**，不是条款/块 | ❌ 块级 / 条款级 |
| **三态：有值 / 原文未写明 / 待人工** | 必须**可证明覆盖**——否则分不清「没有」和「没找到」 | ❌ top-k，覆盖不可知 |
| 同一件事只判一次（材料写「见废标」） | 跨表**事项对齐**，一个事项一个 ID | ❌ 四张表各自独立 |
| 删掉无原文抓手的行 | 抽取每条**必须带 quote**，无 quote 不落表 | ⚠️ verify 段有，未强制 |
| 资格门槛 vs 无效情形 分组 | 抽取要输出**条件类型** | ❌ |

**第 3 条最狠。** 「合同要点的服务期写未写明」这句话，如果用 top-k 检索取数，就永远无法判断是「原文真没写」还是「检索没捞到」。

`输出形式-落地版.md` 规则 5 说「把抽取失败写成未写明，等于把系统的错伪装成文件的错」。反过来就是：**要么做到可证明覆盖，要么这条规则只是漂亮话。**

这比「覆盖率不可控」的论点硬——不是「更好」，是「不做就无法满足输出」。

## 三、三层架构

```
┌─ 第一层：解析（结构）────────────────────────────────┐
│ 页 → 章 (section_types)                              │
│    → 条款树 (parent_id, clauses.py)                  │
│    → 句 (bbox + modal + consequence + ★)   ← 新增     │
│    → 表 (header_levels + spans + inherited)          │
│    → 键值表 (前附表：条款号 | 项目 | 编列内容) ← 新增  │
└──────────────────────────────────────────────────────┘
              ↓ 提供「可定位的最小证据单元」
┌─ 第二层：取数（事项 × 层 × 形态）────────────────────┐
│ 事项 = 输出的一行（一个废标条件 / 一个材料项…）        │
│ 每个事项声明：出现在哪几层、每层什么形态               │
│   表形态    → 直读                                   │
│   键值形态  → 直读（前附表）                          │
│   短条款    → 定位器(情态∪后果∪★) → 全过              │
│   长文      → 检索（保留）                            │
│   公式      → 正则                                   │
└──────────────────────────────────────────────────────┘
              ↓ 候选（每条带 quote + page + role + 类型）
┌─ 第三层：聚合（对齐 / 条件句化 / 分档 / 三态）───────┐
│ 事项对齐（跨表去重：材料「见废标」）                   │
│ 条件句化（「不能 X，否则 Y」→「若 X」）                │
│ 分档（必废 / 需确认 / 非投标人，按原文措辞）            │
│ 三态（有值 / 未写明 / 待人工，靠覆盖记录）              │
└──────────────────────────────────────────────────────┘
```

**和现在差别最大的是第三层——它不存在。** 现在抽取完直接落表，没有对齐、没有条件句化、没有三态。

## 四、解析层要补的第一个产物：句级 + 情态词

`parse.py` 到块，`clauses.py` 到条款。输出要 `p23 无效句` 这种句级 role，中间缺一层。

在条款内部切句（按 `。；` + 编号边界），每句带：

```python
Sentence(
    text,            # 句原文，不改写
    bbox, page,      # 句级定位
    clause_id,       # 属于哪条
    modal,           # 不得 / 不能 / 禁止 / 应 / 须 / 必须 / 未 / 不予
    consequence,     # 投标无效 / 否决 / 不予受理 / 不得参加 / 取消资格
    star,            # ★ / ▲（句首，不是单元格文字）
)
```

有了这个，三条硬规则**有了必要条件——但还不充分**。「情形 = 条件句」还要靠聚合层的条件句化（规则 1 踩过的坑正是改写丢「不能」），句层只是给了原材料：

| 输出规则 | 满足方式 |
|---|---|
| 情形 = 条件句 + 情态词 | 有 `modal` 和原句，可代码转换 |
| 页码带 role | 有句级 bbox，`consequence` 非空 → `无效句` |
| 无抓手就删 | 没 `consequence` 也没 `modal` 的句子根本不进候选 |

**这是最该先做的一层**：切句是纯代码，零模型，收益直通输出。

## 五、事项 × 层 × 形态矩阵

依据 `sample/招标文件竖向结构.md`：**同一事项多层重复，各层承载不同属性**（`:177`）。

### 5.0 实测：一个事项散在几章（2026-11-22 复跑，全对）

| 事项 | 北京 | 崇左 | 温岭 |
|---|---|---|---|
| 投标保证金 | **4 章**（notice×31 / qualify×2 / score×1 / format×1） | 3 章（notice×3 / invite×2 / format×1） | **1 章**（invite×2） |
| 联合体 | **6 章**（notice×13 / format×10 / contract×8 / qualify×7 / score×3 / invite×1） | 4 章（notice×51 / format×32 / contract×5 / invite×1） | 2 章 |
| 最高限价 | 4 章（score×5 / demand×2 / invite×1 / notice×1） | 2 章 | 2 章 |
| 实质性 | 4 章（format×14 / score×8 / notice×6 / qualify×1） | 4 章 | 4 章 |
| 履约保证金 | 1 章（format×1） | **2 章（contract×8 + notice×6）** | 2 章 |
| 资格审查 | 4 章（qualify×11 / notice×4 / score×2） | 1 章（notice×11） | 1 章（notice×7） |
| 符合性审查 | 1 章（score×15） | 2 章 | 1 章 |

**两条硬结论：**

1. **分布形态因文件而异**：北京高度分散（联合体散在 6 章），温岭高度集中（投标保证金只在公告出现 2 次）。**任何写死的 `section_types` 路由，在这两份文件里必有一份是错的。**

   → **准确说法：`section_types` 不能再单独决定「去哪取」，但它没失效。**
   - **去哪取**：由事项矩阵给出的**候选层集合**决定（可跨文件不同），再加定位器确认
   - **章类型仍用于**：定性（这段是须知还是格式）、分包、**降权**（格式章的模板句、合同章的履约句要压权重）
   - 反过来也不能滑到「全文无差别扫」——那会把成本和假阳性一起拉回来

2. **「按章黑名单」挡不住**：崇左的履约保证金在**须知章出现 6 次**。所以「不扫 format 章」这种规则是错的，必须按**表述类型**排除（`exclusive_pairs`：投标保证金 ≠ 履约保证金），不能按章排除。

三份样本的章分布（页）：

| 章 | 北京 | 崇左 | 温岭 |
|---|---|---|---|
| 公告 | p3–6 | p3–8 | p3–5 |
| 须知 | p7–22 | p23–42 | p6–17 |
| 资格 | p23–25 | 并入须知 | 并入公告 |
| 评标 | p26–35 | p43–49 | p18–21 |
| 需求 | p36–43 | **p9–22** | p22–35 |
| 合同 | p44–68 | p50–63 | p36–39 |
| 格式 | p69–92 | p64–94 | p40–64 |

## 六、聚合层：五个动作

**核心动作不是去重，是「把散在 1–6 章的副本拼成一张卡」。**

| 动作 | 输入 | 规则 | 输出 |
|---|---|---|---|
| **① 字段级多源合并** | 同一事项的多副本 | 每个副本只填它那层的字段，**不互相覆盖**（见下例） | 完整事项卡 |
| **② 跨表去重** | 多张表的行 | 已在 ② 判过的材料 → 写「见 ②第 N 条」，不再重复判定 | 唯一事项 ID |
| **③ 条件句化** | 原文规范句 | `不能 X，否则 Y` → 条件「若 X」，后果 Y；`X 的，Y` → 「若 X」 | 情形 + 后果 |
| **④ 分档** | 后果词 + 是否附条件 | 投标无效/否决 → 必废；带「如/视」→ 需确认；主体非投标人 → 非投标人 | 档 |
| **⑤ 三态** | 该事项的层覆盖记录 | 层全过 + 无候选 → `未写明`；层未过/抽取失败 → `待人工` | 状态 |

### 6.1 为什么必须字段级，而不是「一行一条来源」

现在的 `FeibiaoRow` 是**一行一条来源**：命中须知就落一行、命中前附表就落一行。结果同一个保证金出现 3–4 行，每行只有一个字段有值，**永远拼不出完整一张**。

实测的四个副本，各管一个字段：

| 事项：投标保证金 | 层 | 形态 | 填哪个字段 |
|---|---|---|---|
| 金额 8000 元 | 公告 / **前附表** | 键值 / 三列表 | `amount` |
| 缴纳方式、到账时点 | 须知正文 12.1–12.2 | 短编号条款 | `method` |
| 未按期交纳 → 投标无效 | 须知正文 12.3 / 评标符合性 | 短句（后果词） | `verdict` |
| 凭证 / 担保函模板 | 格式章 | 空表 | `evidence` |

拼出来的卡片：

```yaml
事项: 投标保证金
amount: 8000 元            refs: [p8 金额]
method: 电汇/银行保函，截止前到账  refs: [p17 期限]
verdict: 未按期交纳 → 投标无效    refs: [p17 无效句, p26 无效句]
evidence: 投标担保函（格式章模板）  refs: [p70 格式]
多源覆盖: 4/4 章
```

**这张卡才是 `输出形式-落地版.md` 里 ③ 那一行需要的。** 按「一行一条来源」落表，输出层还得自己再聚一次——那还不如在聚合层做完。

### 6.2 冲突不裁决

同一字段两处不同值（公告写 8000、前附表写 7000）→ **两个都留，标 `conflict`，refs 各带页码**。不自动选一个，因为选错无人能查。

**三态的判定要用覆盖记录，不是靠模型说「没找到」。** 这是第二层必须留 `pack_covered` / `layer_scanned` 的原因。

## 八、落地顺序

按「输出能不能成立」排，不按技术优雅。

| 步 | 做什么 | 为什么排这里 | 产出数字 |
|---|---|---|---|
| **1** | 条款内切句 + `modal` / `consequence` / `star` | 输出的三条硬规则全依赖它；纯代码零模型 | 句数、含情态句占比 |
| **2** | 前附表直读（键值表） | ③①⑤ 多个字段的权威来源，现在完全空白 | 前附表项数 |
| **3** | 事项 × 层矩阵落成 YAML | 架构骨架；不写会退回「按章扫」 | 事项数 × 层数 |
| **4** | 聚合层：条件句化 + 分档 + 三态 | 输出形式成立与否就看这层 | 三态分布 |
| **5** | 短条款按矩阵全过（废标 / 材料） | 覆盖率可证明 | 覆盖率 |
| **6** | 检索降级为 `ask_box` / `_follow` | 最后 | — |

### 8.2 四条施工约束（比顺序更重要）

1. **步 3 不要一次铺六块矩阵。** 先只做「投标保证金 + 最高限价」两张事项卡跑通多源合并，再扩联合体/材料。一次铺满 YAML 骨架很大，门禁归因也拆不开。
2. **步 4 的「未写明」依赖步 5 的覆盖记录。** 顺序上 4 在 5 前，所以先只做「有值 / 待人工」两态，等 `layer_scanned` 就绪再开第三态——否则做的就是假三态。
3. **补「公司对照放哪」这一刀。** `输出形式-落地版` 的 ①/② 分组和结论条都依赖 `company.yaml` 判定，但本文聚合层没写它在哪发生。**不写清会变成「抽完就当核对完」**——和旧审阅里「Map 之后谁比对」是同一个问题。

   建议：聚合层之后单独一次，只做「事项卡 × `company.yaml` → verdict/依据」。抽与判分离，两者可分别评估。

4. **别和步 1 并行大改检索。** 检索降级（步 6）等事项路径稳定后再动。

### 8.1 新增的可判错指标：多源覆盖率

```
多源覆盖率 = 该事项 refs 覆盖的章数 / 该事项在全文出现的章数
```

用实测数据就能算，不需要金标：

| 事项（北京） | 全文出现 | 要覆盖 |
|---|---|---|
| 投标保证金 | 4 章 | notice / qualify / score / format |
| 联合体 | 6 章 | notice / format / contract / qualify / score / invite |
| 履约保证金（崇左） | 2 章 | contract / notice |

**这个数字比「金标召回」好算也好解释**：一个事项散在 4 章，只抽到 1 章，覆盖率就是 25%——不用人工标对错。

它同时是「三态」的判据来源：某章没覆盖到，那个字段就只能标 `待人工`，不能标 `未写明`。

## 九、代价

代价要分两笔算，别捆成一句：

| 种类 | 代价 | 可压缩吗 |
|---|---|---|
| **解析变重** | 句级是新维度，`INDEX_VERSION` 再升一次，全量重建索引 | 不能，一次性的 |
| **LLM 次数** | 不一定涨到 20 次：表直读、前附表直读、正则全扫都是零模型；只有「短条款全过」和「长文」才调模型。**矩阵做实后次数取决于候选条款量，不取决于章数** | 能，靠定位器收紧候选 |

**门禁先变差是必然的**，但原因不是精度退化，是**题面过期**：21 题按「页命中」设计，新架构要判「行存在 + role + 三态」。步 4–5 之前不该认基线，步 5 之后要同步改题面期望，否则永远红。

换来的是 `输出形式-落地版.md` 那五条规则真的能实现。
