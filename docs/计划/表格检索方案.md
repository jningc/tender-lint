# 表格检索：从「抽出来」到「检索得到」

> 面试讲解版。项目：招投标文件核对系统（`~/Desktop/tender-lint`）。
> 核心问题：表格里的数据关系（谁是谁的子项、合计等于哪几项之和）是 LLM 不擅长的，
> 而 RAG 又要求「每块能被检索到」。这两件事怎么同时满足。
> 表外还有一种评分规则（计算公式写在正文）：见 `docs/计划/评分规则两种载体.md`。

---

## 一、先给结论

**表格检索不用把表格翻译成 LLM 生成的文字段落，而是用代码模板把「列名 + 单元格值」拼成结构化文本（small），命中后再返回整张表（big）。**

一句话理由：表格已经被正确解析出来了，再让模型「读一遍图、重新写一遍」是把已正确的结构化数据丢进会重新出错的黑箱——而且同一行跑两次结果不一样，回归测不了。

---

## 二、问题是什么

### 2.1 表层问题

投标文件的评标办法里有评分表，长这样（北京样本 p33）：

| 分类             | 序号  | 评审因素       | 分项  | 合计        | 评审标准               |
| -------------- | --- | ---------- | --- | --------- | ------------------ |
| 商务部分（10分）*跨3行* | 1   | 类似项目业绩     | 4分  | 10分 *跨3行* | 具有近三年…每个2分，满分4分    |
|                | 2   | 总监理工程师类似业绩 | 3分  |           | …1个以上（含）3分，没有业绩不得分 |
|                | 3   | 体系认证       | 3分  |           | …有一个得1分，满分3分       |

要回答「商务部分多少分」「没业绩得几分」，必须同时拿到三样东西：

1. 某一行的**评分因素 + 分值 + 评分标准**
2. **表头**（`4分` 是「分项」还是「合计」）
3. **表级事实**（`10分` 是三项之和，不属于任何单项）

### 2.2 为什么这是真难点

- **行脱离表头就没有意义**。`4分` 单独成一块，不知道是谁的分、是分项还是合计。
- **列名和值的关系是二维的**，而文本是一维的。随便切一刀就断。
- **合并单元格让「一个值属于多行」**。`商务部分（10分）` 跨 3 行，`10分` 跨 3 行。按行求和会把合计加 3 遍。
- **LLM 不擅长算关系**，擅长读句子。所以不能指望它从一堆散块里自己拼出 `4+3+3=10`。

### 2.3 现有 RAG 方案在这里为什么不够

RAGFlow 有个真实 issue（#10844）描述的就是这个：默认把表当独立 chunk，结果**纯数字表语义检索命中不了**——用户问「销售增长趋势」，表里只有数字没有「增长」「趋势」这些词，检索直接跳过，只召回旁边那段说明文字。

官方补丁是给表配一个 `table context window`（表前后各取 N token 的说明文字一起进 chunk）。这解决「表有没有语义」，但没解决「行脱离表头」。

## 三、我的思考过程（按顺序，含每步的判断依据）

### 第 1 步：先确认表抽得对，再谈检索

如果抽表本身错了，后面所有设计都是空谈。所以先把「抽得对不对」变成可判错的问题：

- 表头两级？`['分类','序号','评审因素','标准分','标准分','评审标准']` / `[..., '分项','合计', ...]` ✅
- 合并单元格？`{col:0, rowspan:3}`、`{col:4, rowspan:3}` ✅
- 值对不对？`4分 / 3分 / 3分`，`Σ分项 = 10 = 合计` ✅
- 跨页能接上？chongzuo p46+p47+p48 三页接成 9 行 ✅

**判断依据**：能对着 PDF 逐字核。做不到这一步，后面全是猜。

### 第 2 步：看业界怎么切表

调研了四种主流（都看过原文）：

| 方案                                                           | 做法                 | 实测结论                                                       |
| ------------------------------------------------------------ | ------------------ | ---------------------------------------------------------- |
| **Table-as-a-Chunk**                                         | 整表一块               | 中小表最稳，但检索粒度粗                                               |
| **Header + Row**                                             | 每行配列名，做成 key-value | 文中明确说是「行式数据必须」——**不带表头会丢意义**                               |
| **LlamaIndex HierarchicalNodeParser + AutoMergingRetriever** | 叶子检索，超阈值合并回父节点     | 实测收益极小：correctness 4.27 vs 4.21，relevance 0.9167 vs 0.9167 |
| **ColPali**                                                  | 直接对页面图像做多向量嵌入，跳过解析 | 检索强，但给不了结构化输出（没有 bbox、没有数值、没有合并关系）                         |

**判断依据**：ColPali 那条路走不通，因为我的交付要求「证据能回到页码和 bbox」，还要报 `Σ分项=合计` 这种可判错的数字。视觉检索只解决「找到哪一页」。

### 第 3 步：拆自己的思路，发现「读图 LLM」是多余的一步

我最初的想法是：拿一个读图 LLM，把每行规范成文字段落，表格转文字，利于 RAG。

**这一步被我自己否掉了，两个理由：**

1. **文本层已经抽对了。** `4分`、`10分`、`商务部分（10分）` 逐字和原图一致。让视觉模型再看一眼图重新生成，等于把已正确的数据丢进会重新出错的环节。
2. **不可复现。** LLM 生成同一行两次可能不一样，回归门禁没法用——同一题今天过明天不过，分不清是改坏了还是模型抽风。

具体差在哪，举个例子：

| | 模板拼 | 读图 LLM 生成 |
|---|---|---|
| 输出 | `在担任总监理工程师职务下的类似监理业绩；1个以上（含）3分，没有业绩不得分。` | 「投标人提供总监理工程师类似业绩，**一个及以上**可得3分，无业绩则不得分」 |
| 问题 | 无 | 「1个以上（含）」被改写成「一个及以上」，**丢了括号里的「含」**——边界条件变了 |

在核对场景里，「含不含 1 个」决定 3 分还是 0 分，而改写是悄无声息的。

### 第 4 步：保留 small-to-big 的骨架，只换 small 的生成方式

方向是对的（细粒度检索、粗粒度使用），只需要把「LLM 生成段落」换成「代码模板拼字段」。

## 四、方案

### 4.1 数据结构（已实现）

```
章节（section: 第三章 资格审查与评标办法）
  └── 表（table: beijing_road:p33:2）   ← 靠 pages 落在章节页码区间里挂上去
        └── 行（row: row_index 0/1/2）  ← 带 spans（合并）+ inherited（继承标记）
```

表的 id 用 `文档:首页:页内第几张`（`beijing_road:p33:2`），不用列表下标——下标会随合并逻辑变化整体前移（实测 `t006` 变成 `t009`），题集里的 id 全废。

### 4.2 small：模板拼（**不经过任何模型**）

```python
def small_chunk(t, row):
    lv = t.header_levels[-1]                    # 最细一级表头
    fields = {lv[i]: row.cells[i] for i in range(len(lv))}
    total = t.checks().get("total")             # 表级事实：合计 10
    return (
        f"[评分表 {t.id} 第{row.row_index+1}/{len(t.rows)}行｜{fields['分类']}]\n"
        f"评审因素：{fields['评审因素']}｜分项分值：{fields['分项']}｜"
        f"本表合计{total}分（{len(t.rows)}项）\n"
        f"评审标准：{fields['评审标准']}"
    )
```

输出（真实数据，逐字来自 cells）：

```
[评分表 beijing_road:p33:2 第2/3行｜商务部分（10分）]
评审因素：总监理工程师类似业绩｜分项分值：3分｜本表合计10分（3项）
评审标准：在担任总监理工程师职务下的类似监理业绩；1个以上（含）3分，没有业绩不得分。
```

三个设计点，每个都对应上面的一个坑：

1. **字段名进 chunk**（`分项分值：` 而不是孤零零的 `3分`）—— 绕开 RAGFlow 那个「纯数字表检索不到」的坑，字段名本身就是语义。
2. **表级事实进每一行**（`本表合计10分（3项）`）—— 否则问「商务部分一共多少分」，三条 chunk 各自只有 4、3、3，谁也不知道 10 是总数。这是 RAGFlow 坑的镜像版。
3. **原文不改写** —— 保留「（含）」这种边界词。

### 4.3 big：命中后回整张表

拿 `table_id` 把整表 `to_html()` 取出来（合并关系用 `rowspan/colspan` 表达），连同章节标题一起给 LLM：

```
【第三章 资格审查与评标办法 · 商务部分 10分】
<table>…3 行 6 列，分项/合计 两级表头…</table>
公司情况：{company.yaml}
```

LLM 看到的是完整一张表，能自己核 `4+3+3=10`，也能看见「没有业绩不得分」这行就在同一格里。

### 4.4 判定输出

按 `PingfenRow` 存：`item / score / standard / company / verdict / refs(bbox)`。

**关键取舍**：`PingfenRow` 不强行拆成三个字段——表结构本身不统一（有的表分值在独立列，有的写在「质量控制措施(8分)」的文字里）。所以行对象保留原始 `cells` + 引用 `header_levels`，判分时按列名找，找不到再从文字里正则抓。硬拆的结果是 35 行里只有 15 行能填满（43%）。

## 五、怎么验证（可判错的指标）

建 20 条查询，每条只认一个答案：

| 查询 | 答案 |
|---|---|
| 商务部分一共多少分 | 10 |
| 类似项目业绩每个得几分 | 2 |
| 体系认证拿满分要几种认证 | 3 |
| 总监理工程师类似业绩没业绩得几分 | 0 |

两个指标：

1. **small chunk 召回率** —— 该行有没有被召回
2. **big 返回里有没有答案** —— 整表给过去，LLM 答对没有

有这两个数，方案好坏当场能判，不用讨论。

## 六、实测结果

**已实现**：`tender/table_chunks.py`（small chunk + 表级事实 + BM25 检索）、`eval/table_queries.json`（20 条）、`eval/table_recall.py`（评测）。

| 指标 | 结果 |
|---|---|
| 表级召回 | **20/20** |
| 行级召回 | **19/20** |
| 答案在场（整表里有答案） | **20/20** |
| 唯一漏项 | 「商务分满分多少」——命中了 chongzuo 那张表，但没命中第 6 行 |

全部 20 条查询和期望答案都在 `eval/table_queries.json`，可复跑。

### 表级事实的三种证据强度（这是设计里最关键的一处）

| 情况 | 输出 | 例子 |
|---|---|---|
| 原文写了合计（行或列） | `本表合计10分（3项）` | `p33:2` 第 5 列；`wenling` 末行「总分 50」 |
| 没合计，但每一项都抓到分值 | `Σ分项60分（8项，推定；原文未声明合计）` | `p33:3` 技术部分 |
| 项数对不上（有行没抓到） | **空，不写** | `chongzuo` 9 行只抓到 8 项，累加会得 100，实际 80 |

第三条是被实测逼出来的：漏一项少算、重复一项多算，**错数字比没数字更糟**，所以宁可空着。

### 过程中踩到的三个坑

1. **`'分项' in '评分项目'` 是 True**——用 `in` 找列名，把「评分项目」当成了「分项」列，算出「投标报价（30分）」= Σ分项 30 分的假事实。改成精确匹配优先。
2. **重复表头**：chongzuo 的表头是两个「序号」，第二列实际是分类（值「商务分（满分20分）」）。不去重的话 chunk 里没有「商务分」这个词，检索不到。
3. **只把第一列当分类**：北京的表分类在第 1 列、chongzuo 在第 2 列，写死列号就会漏。

### 接进主流程之后（`node_pingfen`）

抽取环节不用 small chunk 检索，而是**逐表喂整表 HTML**——抽取要的是全量，不是「哪一行最相关」。small chunk 那条线留给问答侧（用户问「商务分多少」时用来定位表）。

实测输出：

```
beijing_road:p33:1 → 1 条      （报价 30 分）
beijing_road:p33:2 → 3 条      （商务 4/3/3）
beijing_road:p33:3 → 8 条      （技术 8 项）
chongzuo_green:p46:1 → 12 条   （9 行，模型把合并的子项拆开了）
wenling_video:p19:1 → 12 条 + 表外补充 1–3 条
```

回归门禁（三份样本、每份跑 3 次取多数）：

| 指标 | 表线接入前 | 接入后 |
|---|---|---|
| 正例 | 12/18 | **14/18** |
| 负例 | 3/3 | 3/3 |
| 违规 | 0 | 0 |
| flaky | 0 | 1（`wl-bond`，不是评分表题） |
| ★ 覆盖页 | 1 | 1 |

### 接入时踩的两个坑

1. **只喂表会丢表外规则**（掉分主因）。温岭的评分规则分两处：p18 正文写「投标报价得分=(评标基准价／投标报价)×50%×100」，p19–21 才是评审表。表线只把表 HTML 喂给模型，模型看不到 p18，「评标基准价」这条评分项就抽不出来，`wl-price` 判 miss（第一轮 12/18 掉的就是它）。补法是抽完表再做一次条款检索（`价格分 报价 评标基准价 计算公式 满分`），按评分项名去重后合并。
   **根因**：评分规则有两种承载形式——表格式（评审项 × 分值）和文字式（计算公式）。只做表，只覆盖了前一种。
   **专篇**：现象、思考、改法见 `docs/计划/评分规则两种载体.md`。`node_pingfen` 已加 score 章公式扫描，BM25 价格分 query 暂留作双保险。
2. **同一个能力有两条入口，只给一条传了参数**。v1（`workflow.py:466`，`main.py check` 用）和 v2（`stages/parse_stage.py`，门禁和网页用）各自建索引；`tables` 只传给了 v2。因为门禁走 v2，这个漏洞**门禁完全测不出来**——它会静默退回条款检索，日志也没有区别，直到有人用命令行跑才表现为「同一份 PDF，网页抽 12 条、命令行抽 8 条」。
   **这类 bug 不是逻辑错，是覆盖不全**：改了函数，另一个调用点没跟着改，而测试只覆盖了其中一条。
   **现状**：默认引擎已切 v2，`check` / `index` / `ask` / v1 回退的建库都走 `parse_stage`，坑 1 主路径已收口。`TableIndex` 仍只给问答评测用，不进抽取。

### 提示词里必须加的一条

```
表可能有两级表头（如「标准分」下面分「分项」和「合计」）。
「分项」是这一项的分值，「合计」是本类几项之和——score 填分项，不要填合计。
```

不写这句，模型会把「合计 10 分」当单项分值：三条各 10 分、加起来 30 分。

## 七、面试可能被追问

**Q：为什么不用 LLM 生成段落？模型写得比模板通顺。**
通顺不是目标，**边界条件不丢**才是。原文写「1个以上（含）」，模型优化语言时会把「（含）」吃掉，而这一条决定 3 分还是 0 分。另外同一行跑两次结果不同，回归门禁失效——我改代码后跑评测，分不清是改坏了还是模型抽风。

**Q：那什么时候该用读图 LLM？**
扫描件。文本层不存在时才需要 OCR/VLM。我这三份样本都是文本型 PDF，`page.get_textbox()` 就能拿到逐字正确的原文，没有理由绕一圈。

**Q：small-to-big 不是会丢上下文吗？**
small 里已经塞了表级事实（合计、共几项）和表头字段名，丢的只是同表其他行的正文——而命中后 big 会把整表补回来。LlamaIndex 那个 AutoMergingRetriever 的实测收益很小（4.27 vs 4.21），说明合并策略本身不神奇，关键是 small 有没有携带足够上下文。

**Q：表头两级，模板怎么知道哪列是「分项」？**
`header_levels` 最后一级就是最细的表头（`['分类','序号','评审因素','分项','合计','评审标准']`），按位置对到 cells 上。粗一级的「标准分」跨两列，已经填充到子列了，所以不会丢。

**Q：合并单元格怎么处理？**
`cells` 是稠密的（每行都填值，方便直接用），同时用 `inherited` 标出哪几格是从上方继承的，`spans` 记结构（`{col:0, rowspan:3}`）。求和、去重一律用 `inherited=False` 的格——不然合计会被加 3 遍。

**Q：这套东西的可迁移性？**
任何「表格里带层级和合并」的文档都在这个范围内：财务报表、检测报告、报价单。差别只在表头识别和合并判定，骨架（表头层级 + 稠密值 + inherited + spans + 三种视图）是通用的。
