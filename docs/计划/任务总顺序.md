# 任务总顺序（结构先行）

**实施与面试主线见 `docs/计划/轻量主线架构.md`**（双轨核对 + ask_box；B4 只做小切片，c/d 冻结）。

**主线判断：文档结构是一切的下游。** 结构没定稿就动检索，等于在地基上盖房——检索的每个参数（k、query、融合方式）都依赖「切出来的单元有多长、边界在哪」；结构一变，参数全要重调，门禁白跑一遍。

所以顺序是：**结构收口 → 结构接检索 → 内容层 → 评测收尾**，不是按「哪个看起来收益大」排。

本文合并了三份文档：`docs/归档/迁移计划.md`（阶段 0–4 已完成）、`docs/归档/下一步任务.md`（T0/T2a/T2b 已完成）、`docs/规则/条款口径.md`（定稿，作为 A 段验收依据）。

**B1-b 检索融合改造（✅ 完成 2026-11-22：BM25 + RRF）**

改的是 `tender/index.py:SectionIndex.search()`：从「BM25 取 k 条 + 向量取 k 条、合并去重」换成 **RRF 融合**（`score = Σ 1/(RRF_K + rank + 1)`，`RRF_K=60`，取 Azure AI Search 默认值）。

每条命中新增 `score`（融合分）和 `recall`（`bm25` / `vec` / `bm25+vec`），后者用来定位「排序退化到底退在哪一路」。开关 `TENDER_FUSION=rrf|union` 可 A/B 对比。

**实测（同一套 21 题）：**

| 指标 | union（旧） | rrf（新） |
|---|---|---|
| 正例 | 15/18 | 15/18 |
| 稳定题 | 14/17 | 13/16 |
| ★ 覆盖 | 2 | 2 |
| flaky | 1 | 2 |

**第一次测：命中数持平、稳定题 -1。** 追查下去发现**不是 RRF 的问题，是两个 bug**：

1. **合并键太粗**：`key=(page, text[:40])`——`chunk_pages` 切段有重叠，相邻 chunk 前 40 字相同，被判成同一个 chunk 折叠掉，BM25 的 top-8 实际只剩 4–5 条，RRF 没有排序空间。改成 `(page, 全文)`。
2. **合并后又按页码重排**：`TenderIndex.search` 里 `hits.sort(key=page)`，**把每个 store 内部的排序（含 RRF）彻底抹平**。相关性排序从来没进过模型，`_hit_blob` 的 8000 字预算也按页码截断。

修完后三种排序的真实表现（21 题，正确页出现在前 8 名的比例）：

| 排序 | MRR@8 | top1 | top8 覆盖 |
|---|---|---|---|
| 页码（原状） | **0.4763** | 39% | 72% |
| BM25 优先 | 0.4358 | 28% | **83%** |
| RRF | 0.3470 | **11%** | 72% |

**两个反直觉结论：**

- **页码排序的 MRR 高是评测偏差**：答案页集中在 p3/p4/p8（公告、须知开头），页码升序天然占优。按「模型能看到的前 8 条」算覆盖，BM25 优先最好（83% vs 72%）。
- **RRF 在这套 query 上最差**（top1 11%）：RRF 惩罚「只在一路出现」的条目——BM25 排第 1 但向量没进 top-8 的条款只拿 `1/61`，被「两路都排第 5」的（`1/66+1/66`）压过去。关键词串 query 上，BM25 判断比向量准，融合反而稀释。

**端到端验证（BM25 优先 + 不重排）**：正例 14/18、★ 覆盖 2→**3**、flaky 1→**3**。检索指标更好，但分数掉 1、稳定性变差。

**根因**：`_hit_blob` 把命中拼成**一整段连续文本**喂模型——按页码排才连贯，按相关度排会让文本跨页跳跃、上下文断裂。**「选哪些」和「按什么顺序喂」是两件事，现在共用一个顺序。**

**当前决策**：默认回到 `order="page"`（15/18、flaky 1），保留 `order="relevance"`（给 `ask_box` 单条证据问答用）。**下一步是两段式**：按相关度选 top-N，喂之前按页码重排，约 10 行。

**原计划（已作废）**，原计划改 `tender/index.py:248` 的 `SectionIndex.search()`：现在是「BM25 取 k 条 + 向量取 k 条，合并去重」，问题在 BM25 靠词频、条款短（中位 51–62 字）时信号弱。

**为什么让路**：主路径从「检索 top-k」改成「定位器 + 有限打包抽取」后（见 `docs/计划/检索与扫描架构.md`），检索只服务 `_follow`（跨章引用）和 `ask_box`（用户提问）。**调 BM25 排序对六张表没有收益，只对问答有。**

改到什么时候：等 B4 落地、六张表不再走检索之后，作为 `ask_box` 的专项优化再做。那时的做法是索引侧（`context` 进 BM25）而不是查询侧（`expand_query` 已证明会掉分）。

### C2 术语注入检索（1 天）**❌ 试过，已回滚**

做法：六张表的 query 末尾追加 `expand_query()` 展开的别名，**k 不动**——k 一改，分数变化说不清是谁的功劳。

**实测（2026-11-17）**：`expand_query` 把每个标准词的别名 + `weak` 泛词都塞进 query，长度涨 3–5 倍，BM25 打分被稀释，越扩越差。

| 指标 | 注入前 | 注入后 |
|---|---|---|
| 正例 | 13/18 | **12/18** |
| flaky | 1 | 3 |
| 违规 | 0 | 0 |

已全部回滚（5 处 `expand_query` 调用和 import 都删掉）。结论：**别名扩召回不能靠拼 query 字符串**——要么在索引侧做（同义词表进分词/倒排），要么只对命中率低的单张表定点调。同一个词表放进 query，会把无关表一起拉高。

## 七、为什么不是先做术语表

我之前排的是「术语表优先」，改成现在的顺序，理由是**术语表会改检索**：

- C1 不改行为，可以做在任何时候；
- **C2 注入 query 是改行为**，必须跑门禁。如果 B1 还没做（检索融合要重写），C2 做完再过一遍 B1，等于同一个门禁跑两轮、还要把「分数变化归因到术语还是融合」拆开——拆不开就是白跑。

所以顺序是「**先让检索层定稿，再往里加内容**」，不是「哪个收益大先做哪个」。
