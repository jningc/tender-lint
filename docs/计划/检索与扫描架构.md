> 已取代：顶层的**组织维度**——本文按「表 → 章」路由，新架构按「事项 × 层 × 形态」组织（见新文档第五节）。
>
> 2026-11-17。取代 `检索改造方案.md`（那份只讲到「检索内部怎么调」，漏了更上一层的问题）。
>
> 起点是一个判断失误：**六张表是「固定 schema 的信息抽取」，不是「问答」。拿检索（top-k）做抽取，覆盖率天然不可控。**

---

## 一、结论（三句话）

1. **不是所有表都该检索。** 按「字面特征的强弱」分三档：结构直读、正则全扫、章节全扫。
2. **检索降级成辅助工具**——只用于两件事：追跨章引用（「详见第五章」）、用户提问（`ask_box`）。
3. **门禁分数（15/18）证明不了覆盖率。** 21 道题是按「检索能不能命中」设计的，读者会问「那漏了多少」，现在答不出来。要换成覆盖率指标。

---

## 二、三个层次的问题（必须分开解决）

| 层 | 问题 | 表现 | 解法 |
|---|---|---|---|
| **L1 分词** | 单字切在短条款上先崩 | 条款中位 51–62 字，单字切完一半是虚字 | jieba 词 + 字 bigram |
| **L2 同义** | 不同招标文件用不同说法 | 「磋商保证金 / 投标担保 / 投标保证金」 | 索引与查询**双向归一**（不是扩展 query） |
| **L3 架构** | 用检索做固定 schema 抽取 | top-8 覆盖 524 条款的 1.5%，漏了什么不知道 | 按表分流：直读 / 正则 / 全扫 |

**L1、L2 只在「还要用检索的地方」才有意义**；L3 决定哪些地方还该用检索。

## 三、分表方案（核心表）

| 表 | 取数方式 | 字面特征强度 | 覆盖率 | 调用成本 |
|---|---|---|---|---|
| **评分对照** | **表结构直读**（已做） | 表格结构本身 | 100%（5 张表 35 行） | 0 |
| **时间节点**，投标期 | **正则全扫** | 强（`2026年8月18日`、`15日前`、`7个工作日内`） | 已实测 82% | 0 |

| **材料对照** | **章节全扫 + MapReduce** | 弱（「应提供/须提交/原件/复印件」） | 待测 | ~8 次 |

| **跨章引用** | 检索（保留） | — | — | 低 |

- **格式章不扫废标**：整章是投标书模板，「中标后提交履约保证金」会被误判成废标条件（违规 1 就是这么来的，提示词/hits/行级三种过滤都压不住）

## 四、业界证据

### 4.1 专业产品就是逐条全扫，不做检索

Harvey 的 redline 文档（[harvey.ai/blog/how-to-redline-a-contract-with-ai](https://harvey.ai/blog/how-to-redline-a-contract-with-ai)）：

> The AI scans the entire document against your configured standards, **clause by clause**. […] It applies the same level of attention to **page 47 as it does to page 1**, and it does not get tired, skip sections, or forget to cross-reference definitions.

旧架构（[rebuilding-playbook-review-as-a-multi-agent-system](https://harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system)）正是「分类 → 检索证据 → 写结论」，重写的原因：

> Since each LLM call worked on its own, the context of classification **got lost** during citations and redlines.

### 4.2 论文明确指出 RAG 在「整篇都要读」的任务上有结构缺陷

[arXiv 2608.21237](https://arxiv.org/pdf/2608.21237)（Indexing Long Documents for LLM-Based Analysis）：

> **RAG 的局限**：splitting fragments connections between distant passages and top-k retrieval surfaces only a few, so **whole-document questions return incomplete context**.
> **抽取到结构化表的局限**：precise for filter-style lookups, but **the attributes must be fixed before anyone knows what will be asked**.

第二条对我们的语境是好事——schema 本来就是固定的六张表，不用「等知道问题再抽」，但必须保证「该有的都抽到」。

### 4.3 按文档层级做 MapReduce 显著优于 RAG

[ToM (arXiv 2511.00489)](https://arxiv.org/pdf/2511.00489v1)：

> ToM significantly outperforms existing divide-and-conquer frameworks and **retrieval-augmented generation methods**
> RAG relies on similarity rankings and often **neglects the logical coherence** between retrieved chunks

[arXiv 2610.06902](https://arxiv.org/html/2610.06902v1)（NavTree）补了一条设计原则：**只有叶子节点送给模型，内部节点只做路由**——树的收益来自「导航」，不是「摘要」。

我们的 `clauses.py` 已经建好了这棵树（章 → 节 → 款 + `parent_id`），只是没拿它做 MapReduce。

### 4.4 检索层本身的改造（只在还要用检索时）

**Anthropic Contextual Retrieval**（[原文](https://www.anthropic.com/engineering/contextual-retrieval)）：索引前给每个 chunk 前置上下文说明。

| 做法 | top-20 失败率 | 降幅 |
|---|---|---|
| 标准 embeddings + BM25 | 5.7% | 基线 |
| + Contextual Embeddings | 3.7% | 35% |
| + Contextual BM25 | 2.9% | 49% |
| + 重排（150→20） | 1.9% | 67% |

我们的 `chunk_clauses` 已经生成「父标题链 + 本条」的 context，**但 BM25 索引的是** `text`**，不是** `context`——白送的一步没走。

**ACORD**（ACL 2025，法律合同条款检索，[原文](https://aclanthology.org/2025.acl-long.1206.pdf)）：BM25 做召回 + GPT-4o pointwise 重排 NDCG@10 = **79.7**，微调 cross-encoder 只有 60.9。原文：*"a BM25 retriever paired with pointwise GPT-4o performs best"*。

**含义**：BM25 不用换，缺的是它后面那一层。

**RRF**（[Azure AI Search](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)）：BM25 与向量用 `1/(rank+60)` 融合，`k=60` 是实验最优。我们现在是「合并去重」，不是 RRF。

### 4.5 为什么先不换 SPLADE / BGE-M3

- [SPLADE vs BM25](https://zilliz.com/learn/comparing-splade-sparse-vectors-with-bm25)：SPLADE 是学习式稀疏，**扩展发生在索引侧**，对模糊查询更强
- [BGE-M3](https://arxiv.org/html/2402.03216v3)：一个模型同时出 dense / sparse / multi-vector

不换的理由：换 embedding 要重建全量索引 + 重校准基线；而我们的 query 是**固定领域词**（"投标无效 最高限价 预算"），不是用户口语，语义扩展优势用不上——`expand_query` 那次（14/18 → 12/18）已经证明「往里加词」会拉高无关表。

## 五、MapReduce 的具体做法（废标 / 材料 / 合同）

### 5.1 切片——按条款打包，不按字符切

```
输入：某章所有条款（clauses.py 已有，带 bbox/page）
规则：按字数累加打包，每包 ≤ 8000 字，**不切断条款**，相邻包重叠 2 条条款
输出：[{pack_id, pages, clauses: [{id, page, bbox, text}], text}]
```

为什么不按 arXiv 的 30000 字符：DeepSeek 中文 token 效率低，3 万字符约 4 万 token，一次调用太慢；8000 字约 1 万 token，速度可接受。

### 5.2 Map——每包一次调用，只问该章该管的表

```
for pack in packs:
    prompt = "你是招标文件核对员。下面是第 X-Y 页原文。
              只抽：会导致投标无效或资格不合格的条款。
              每条给：条件原文、出处页、触发后果。这一段没有就返回空数组。"
    candidates += llm(prompt + pack.text)
```

两个关键：

- **一次只问一张表**——schema 太多模型会漏
- **明确「没有就返回空数组」**——否则模型硬凑

### 5.3 Reduce——代码做，不让模型做

```
输入：50–100 条候选（同一条件可能在须知和评标办法各出现一次）
分组 key：条件文本归一化（去标点、去虚词、取前 20 字）
去重：完全相同 → 合并 refs 并集；一方前 20 字包含另一方 → 留长的
冲突：同一 key 出现「允许 / 不允许」相反词 → 两条都留，标 conflict=true，**不自动裁决**
输出：20–30 条
```

**Reduce 必须用代码**：模型去重同一批输入跑两次结果不同，回归测不了；而且容易「合并出一条谁也没说的话」。

### 5.4 落表 + 覆盖率自检

```
输出 FeibiaoRow[]，refs 是 page+bbox 数组
自检：pack 覆盖 = 100%（每段都进过模型）
      去重率 = 表条数 / 候选条数（预期 50%–70%）
```

## 六、实测：时间节点这张表（已跑）

用正则扫三份样本的全文，对比 `04_check.txt` 里时间节点表的页码覆盖。

脚本：`eval/time_scan.py`（`--detail` 逐条列）。

### 北京

| 项 | 数 |
|---|---|
| 正则命中 | **23 处** |
| 表里抽到 | 9 条 / 9 页 |
| 页命中重叠 | 4 页（p4/p8/p18/p21） |
| 表未覆盖的页 | p16、p20、p28、p49、p54、p55、p59 |

未覆盖的 7 页分两类：

**① 投标期真漏（3 处）**

| 页 | 原文 | 表里 |
|---|---|---|
| p16 | 「投标截止时间至少 **15 日前**，以书面形式通知所有获取招标文件的人」 | ✗ |
| p20 | 「自中标人确定之日起 **2 个工作日内**，在北京市政府采购网公告」 | ✗ |
| p28 | 「给予相关供应商的合理时间一般**不少于 30 分钟**」（报价修正） | ✗ |

**② 履约期期限被错归（4 页）**：p49/p54/p55/p59 全是监理合同章的「7 天内」「14 天内」「15 天内」，属于合同要点表，不属于投标时间节点。

### 结论（修正了原先的判断）

**时间节点表不需要全扫。** 日期和期限是强字面特征，投标期 17 处节点，表覆盖 14 处，**漏 3 处 = 18%**。

它该改的是**字段结构**，不是扫描方式：

| 阶段 | 例子 | 归属 |
|---|---|---|
| 投标期 | 获取截止、投标截止、开标、解密、澄清期限、质疑期限 | 时间节点表 |
| 履约期 | 合同签订期、预付款期限、验收期限、质保金退还 | 合同要点表 |

拆完：时间节点表 = 17 处投标期节点（而非「9 条 + 4 条人工看」），合同要点表多 4 条履约期限。

### 可复用的规律

| 表 | 字面特征 | 自动化程度 |
|---|---|---|
| 时间节点 | 日期 / 期限字符串 | ✅ 正则可全覆盖 |
| 评分对照 | 表格结构 | ✅ 表线直读 |
| 空位对照 | `____`、`（  ）` | ✅ 结构可扫 |
| 材料对照 | 「应提供 / 须提交 / 原件」 | ⚠️ 可扫候选，判定要模型 |
| 废标对照 | 「投标无效 / 否决 / 不予受理」 | ⚠️ 同上 |
| 合同要点 | 无固定形态 | ❌ 只能全扫 |

**越靠字面固定的表，正则/结构越管用；越靠语义判断的表，越需要全扫 + 模型。**

## 八、已知的坑（别重复踩）

| 坑 | 现象 | 原因 |
|---|---|---|
| `expand_query` 注入检索 | 14/18 → 12/18，flaky 3 | query 长度涨 3–5 倍，BM25 打分被稀释 |
| 整组兄弟条款拼 context | 正例 15 → 10 | 单条 3000 字，k=6 合计 1.8 万字，提示词爆 |
| 扩检索到 `format` 章 | ★+1 但违规 1 | 投标书模板里的「中标后提交履约保证金」被当成废标条件 |
| query 只换后果词 | `bj-cap/cz-cap/wl-cap` 三题全掉 | 「报价超过最高限价的投标无效」的入口词是「最高限价」 |
| 拿 evidence 的 `clause` 字段判覆盖 | 必然 100%，没信息量 | 那个字段是抽取时绑的，不是几何包含 |
| 按字符切片做 MapReduce | 会切断条款，refs 对不上 | 应该按条款打包（Harvey 的 clause-by-clause） |
| `context` 拼进 BM25 / LLM contextualize | 无增量；父链占 90%，短条款 TF 掉 10 倍 | 见「八之二」：结构链已够，别重复 Anthropic 那套 |

## 八之二、Contextual Retrieval：试过，不做（2026-11-24）

Anthropic 2024-09 的 [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)：
给每个 chunk 前加一段 **LLM 生成的说明**，再建向量和 BM25 索引。官方数字是减少 **49%**
检索失败（加 rerank 后 67%）。

它的前提是「chunk 里没有主体信息」，原文例子是 SEC 财报：

```
"The company's revenue grew by 3% over the previous quarter."
→ 哪家公司？哪个季度？chunk 自己说不出来
```

**招标文件不是这个问题。** 我们的 chunk 自带编号、章标题、父链：

```
第二章 投标人须知 › 12 投标保证金 › 12.1 投标人应按《投标人须知资料表》…规定的金额…
```

### 现状：两件已有，第三件试过没用

| 组成 | 现状 |
|---|---|
| BM25 + 向量 + RRF | ✅ `index.py` `FUSION=rrf`、`RRF_K=60` |
| chunk 带上下文 | ✅ 但**结构提取**（父标题链），不是 LLM 生成 |
| 上下文由 LLM 生成 | ❌ 试过，无增量（见下） |

关键实现（`index.py:175-189`）：BM25 用 `text`、FAISS 用 `text`、`context` **只进 metadata**。
也就是说**父标题链不参与检索，纯粹是命中后给模型看的**——这点决定了下面两个实验。

### 实验一：引用回填（规则版 contextualize）——无效

做法：正文写「见《投标人须知资料表》」时，按编号把附表条目的取值拼进 `context`。
（`2.2 项目属性见《投标人须知资料表》` → 附表 `2.2 → ■服务 □货物`）

| 文档 | 回填条数 | 正例（回填前 → 后） |
|---|---|---|
| 北京 | **7 条** | 7/8 → **7/8（不变）** |
| 崇左 | 0 条 | 3/5 → 3/5（与代码无关） |
| 温岭 | 0 条 | 3/5 → 3/5（与代码无关） |

覆盖 **7 / 1338 节点 = 0.5%**；唯一受影响的北京，命中率一点没动。已删除。
（当时门禁报 13/18「退化」，实际是崇左 `cz-bond` 变 flaky 拉的，与回填无关。）

### 实验二：context 进 BM25——只算没跑，因为算出来就否了

| 文档 | `text` 中位 | `context` 中位 | 短条款（≤30 字）占比 |
|---|---|---|---|
| 温岭 | **45 字** | **166 字** | **36%**（152/422） |
| 北京 | 56 字 | 179 字 | 32%（200/618） |

最极端的一例（温岭）：

```
text   (17 字): '1. 具有独立承担民事责任的能力；'
context(169 字): '第一章 > 招标公告 > 项目概况： > 温岭市雪亮工程…获…'
```

**父链占 90%。** 拼进 BM25 后，query「独立承担民事责任」的 TF 从 `1/17` 变成 `1/169`
（权重掉 10 倍）；而父链里的「投标」「项目」「采购」在每个 chunk 都出现，IDF 直接被拉平。

**所以不做**，除非只取父链的**最后一级**标题（短前缀），那要单独 A/B。

### 结论（面试可直接讲）

1. **不做 LLM contextualize**：与父链信息重叠、1800 次调用 / 3 份文档、且不可复现
   （`temperature=0` 也不保证服务端一致，这轮已经踩过）
2. **不做 context 进 BM25**：稀释 90%，36% 的短条款会被淹没
3. **叙事**：「我的结构链已经承担了 Contextual Retrieval 的工作，而且可复现」——
   这比「我照 Anthropic 博客实现了一遍」有说服力，因为它回答了「什么时候**不该**用」
4. 真要做 ask 专项（短前缀进 BM25），**先给 `ask_box` 扩到 15–20 题**：
   现在只有 5 题，且测的是工具调用对不对，不是短条款能不能召回，A/B 测不出差异
