# MapReduce 全扫实验（2026-11-25）

> 起因：用户问「不希望标书分析遗漏内容。我的项目本质是对标书提问→答案形成 6 块，
> 那要达到全扫效果，问题（query）应该更全面吗？」
>
> 这篇记录从这个问题出发的选型、实验、踩的坑，以及数据能支持什么结论。

---

## 一、先把问题拆对

表面问题：**query 要不要更全？**

实质问题：**「不遗漏」的保证从哪来——query，还是清单？**

| 范式 | 靠什么保证不遗漏 | 上限 |
|---|---|---|
| 问答范式 | query 覆盖到多少 | query 表达力的上限 |
| 清单范式 | 检查项定义得多全 | 清单完整性的上限 |

**项目已经是清单范式**（六张表就是六份清单），所以「问题够不够全」提错了方向。

真问题是：**哪些事项必须用「清单 + 定位器」保证覆盖，哪些可以交给问答。**

---

## 二、选型：分片 vs 树形 vs 检索

### 业界三种做法

| 做法 | 代表 | 适合 |
|---|---|---|
| **检索**（top-k） | [TenderLens](https://github.com/nirmalachundawat/tenderlens)、[bidpilot](https://github.com/GiorgosPanagopoulos/bidpilot) | 「哪一章讲了什么」这类定位问题 |
| **分片 MapReduce**（线性） | 本项目 `docs/计划/检索与扫描架构.md` 5.1–5.3 | **穷举**：要「所有」不要「最相关」 |
| **树形 MapReduce** | [ToM, EMNLP 2025](https://aclanthology.org/2025.emnlp-main.899/) | 定位 + 跨块关系（建 DocTree，自顶向下） |

### 为什么选分片

1. **任务是穷举不是定位**：「所有会导致废标的条款」不需要知道第 3 包和第 7 包的关系
2. **可复现**：分片的 Reduce 是代码，门禁能测；ToM 的建树要聚类+摘要（模型判断），回归测不了
3. **成本线性可算**：4–5 包 = 4–5 次调用，实测 6–13 秒
4. 树形的唯一优势（跨块关系）对本项目无用——`ask_box` 才需要导航，那是旁路

### 顺带纠正一个指标错误

原文档 `5.4` 的自检写的是：

```
自检：pack 覆盖 = 100%（每段都进过模型）
```

**这是假指标**——它证明「每段都喂过模型」，不证明「模型抽全了」。给 8 条 hits 抽出 5 行，pack 覆盖仍然 100%。

正确指标是**输出覆盖率**：

```
覆盖率 = 表里 refs 覆盖的候选条款数 / 全文候选条款数
```

## 三、流程（实际实现）

```
tender/clauses.py  build_clauses()   → 条款树（带 page / clause_id）
        ↓
eval/mapreduce_probe.py  pack_nodes()  按字数打包 ≤8000 字，不切断条款，相邻包重叠 2 条
        ↓
    每包一次 LLM 调用（只问「会导致投标无效/否决/资格不合格的条件」）
        ↓
    match_back()  模型返回的条件原文 → 匹配回条款（前缀互含 40 字）
        ↓
    Reduce：按 clause_id 去重（同一条被两个包抽到，id 一定相同）
        ↓
eval/coverage.py  算覆盖率（分子：被覆盖的候选条款；分母：全文含 MUST_FAIL 的条款）
```

### 关键设计决定

| 决定 | 原因 |
|---|---|
| **不让模型给页码** | 模型给的页码不可靠。让它只返条件原文，代码匹配回条款 → page/clause_id 由代码给 |
| **去重 key 用 `clause_id`** | 文本相似度在跨包时不可靠：「未按招标文件要求提交投标保证金」vs「投标人未按招标文件要求提交投标保证金的」，前 20 字对不上，但它们是同一条 |
| **只扫五章** | `invite/notice/qualify/score/demand`。格式章刻意不扫——投标书模板里的「中标后提交履约保证金」会被误判（`docs/计划/任务总顺序.md` 记过） |
| **Reduce 只去重不做归纳** | 去重后能还原原文；归纳成一句话 = 丢信息。冲突（允许/不允许）两条都留，标 `conflict`，不自动裁决 |

### 几个容易误解的点

#### 1. 「全文候选条款数」怎么来的？

不是人工金标，是**规则筛出来的分母**（`eval/coverage.py` / `mapreduce_probe.py` 同一套）：

1. `build_clauses()` 切出条款树
2. 只留五章：`invite / notice / qualify / score / demand`
3. 条款正文里**出现 `MUST_FAIL` 词**的才算候选（投标无效 / 否决 / 不予受理 / 取消资格…）

```
覆盖率 = 抽到并匹配回的候选数 / 全文候选条款数
```

分母定义比分子更敏感：以前还加「否则 / 未按 / 不得」会把采购人约束、履约要求也算进候选，覆盖率被腰斩（见坑 4）。现在只认强后果词。

#### 2. 「包」是向量吗？是直接给 LLM 吗？

**是原文文字包，不是向量。** 和 BM25 / BGE 那条检索线无关。

- 输入：条款节点的 `text`
- `pack_nodes()`：按字数累加，每包 ≤8000 字，**不切断条款**
- 把包里条款拼进 prompt，**整包送给 LLM** 抽条件

全扫 = 分片喂原文；hybrid 检索 = 先召回再喂。两条路别混。

#### 3. `match_back` / 「前缀互含 40 字」是啥意思？

模型只返回**条件原文句子**，不让它报页码（页码不可靠）。代码要把这句话对回某条条款：

1. 去掉空白
2. 取两边较短一侧、最多 **前 40 字**
3. 若 `A 的前缀 ∈ B` 或 `B 的前缀 ∈ A` → 认为是同一处
4. 匹配成功后，用该条款的 `page` / `clause_id`（代码给，不信模型）

宁可漏配，不要错配——错配会让覆盖率虚高。

#### 4. 包不是互斥的吗？为啥同一条会被两个包抽到？

**故意不互斥。** 打包时相邻包 **重叠 2 条条款**（`OVERLAP = 2`）：包边界上的条款会进两个包，两边 LLM 都可能抽到。

Reduce 用 **`clause_id` 去重**（不用文本相似度）。实验里重复率约 15–16%，就是这 2 条重叠的直接代价——所以 Reduce 去重必须做。

## 四、实验数据

### 打包（成本远低于预期）

| 文档 | 条款数（五章） | 包数 | 包内容 |
|---|---|---|---|
| 北京 | 358 | **4** | 7876 / 7974 / 7966 / 2559 字（p3–44） |
| 崇左 | 297 | **5** | 7913 / 7711 / 7811 / 7938 / 5273 字（p3–50） |

### 覆盖率与行数

| 文档 | 检索覆盖率 | 全扫覆盖率 | 提升 | 行数 | 成本 |
|---|---|---|---|---|---|
| 北京 | 35% | **54%** | +19pp | 18 → 22 | 4 次 / 6.1s |
| **崇左** | **14%** | **71%** | **+57pp** | 13 → **59** | 5 次 / 12.7s |

**规律：检索越差，全扫收益越大。** 崇左检索几乎失效（14%），全扫直接拉到 71%。

### 重复率（验证 Reduce 是否必要）

| 文档 | 原始输出 | 去重后 | 重复 | 重复率 |
|---|---|---|---|---|
| 北京 | 26 | 22 | 4 | **15%** |
| 崇左 | 70 | 59 | 11 | **16%** |

**结论：Reduce 去重必须做**，这是包间重叠（每处重叠 2 条）的直接代价。

### 噪声率（抽查 8 条）

```
✓ p5 [2.] 落实政府采购政策需满足的资格要求：☑专门面向中小企业
✓ p5 [3.] 本项目的特定资格要求：具备林业调查规划设计乙级及以上资质
✓ p5 [5.] 单位负责人为同一人…不得参加同一合同项下的政府采购活动
✓ p5 [6.] 信用中国被列入失信被执行人…

✗ p5 [2、] 投标和开标地点：（1）投标文件提交方式：本项目为全流程电子化项目…   ← 操作说明
✗ p7 [6.] 在线竞标响应（电子投标）说明…                                      ← 操作说明

⚠ p9 [1.] 为落实政府采购政策需满足的要求（1）本招标文件所称中小企业必须符合…   ← 定义
⚠ p9 [2.] 「实质性要求」是指招标文件中已经指明不满足则投标无效的条款…          ← 定义
```

**噪声约 25%**（2/8 明显噪声，2/8 边缘）。

**但噪声不影响覆盖率**：覆盖率算的是「含 MUST_FAIL 的候选条款是否被覆盖」，上面两条操作说明本身不含 MUST_FAIL，不进分母也不虚增分子。所以：

| 指标 | 值 | 可信度 |
|---|---|---|
| 覆盖率 | 14% → 71% | ✅ 可信 |
| 行数 | 13 → 59 | ⚠️ 约 25% 是噪声，需行级校验 |

## 五、踩的坑（都是真 bug）

### 坑 1：`response_format` 被 DeepSeek 拒绝

```
Error code: 400 - This response_format type is unavailable now
```

**原因**：`with_structured_output(schema)` 默认走 `response_format=json_schema`，DeepSeek 不支持。

**修**：必须显式指定 `method="function_calling"`——项目 `workflow.py:150` 一直是这么写的，我新写脚本时漏了这个参数。

```python
llm = get_llm().with_structured_output(PackResult, method="function_calling")
```

### 坑 2：`ClauseNode` 不是 dict

```python
covered = [c for c in candidates if any(c["id"] == cc["id"] for cc in cands)]
# TypeError: 'ClauseNode' object is not subscriptable
```

**修**：`c.id`（它是 dataclass，不是 dict）。

### 坑 3：结果文件的表名是英文键

`eval/coverage.py` 第一次跑出来全是 0：

```
废标对照  候选 90 · 覆盖 0 (0%) · 表 0 行 / 0 refs
```

**原因**：`data/regression/*/r1.json` 的 `tables` 键是 `feibiao / pingfen / cailiao / kongwei / shijian / hetong`，我用了中文表名去取。

**修**：`CANDIDATE_WORDS` 的键改成英文，显示时映射回中文。

### 坑 4：候选词表定义太宽，覆盖率被腰斩

第一版候选 = `MUST_FAIL + ("否则", "未按", "不得", "不予")`，结果：

```
北京 候选 38 · 覆盖 14 (23%)
温岭 候选 53 · 覆盖 12 (23%)
```

**问题**：38 条候选里至少 19 条是噪声——

```
p17 [11.3]  采购人不得向供应商索要赠品、回扣          ← 约束采购人
p21 [26.1.2] 答复的内容不得涉及商业秘密                ← 约束代理机构
p30 [2.5.5]  否则不得享受中小企业扶持政策              ← 「不得享受优惠」不是废标
p40 [3.13]   监理人员不得同时身兼 2 个任务             ← 履约要求
```

**修**：候选只用 `MUST_FAIL`（强后果词），不再加弱词。收窄后：

| 文档 | 收窄前 | 收窄后 |
|---|---|---|
| 北京 | 23% | **50%** |
| 温岭 | 23% | **57%** |

**教训：「覆盖率」的分母定义比分子更重要。** 分母宽 → 覆盖率永远低 → 结论永远错。

## 六、发现的问题（不是 bug，是设计问题）

### ① 全扫 ≠ 全覆盖

北京全扫 54%、崇左 71%，**仍有 29–46% 没覆盖**。

原因：全扫只解决「没给模型看」，不解决「模型看了没抽」。模型对「这段没条件」的判断本身有误判率。

**这不是靠加大包能解决的**，要靠：
- 提高候选召回（但会拉低覆盖率分母）
- 或接受这个损失，用「三态」标注（有值 / 原文未写明 / **待人工**）

### ② 全扫必须配行级校验

25% 噪声必须靠代码挡，不能靠提示词（试过「不要硬凑」，模型还是会凑）。

```python
CONSEQ = MUST_FAIL + ("否则", "未按", "不得参加")
if not any(k in condition for k in CONSEQ):
    降级 / 标「待确认」
```

**注意这和之前试过的两种方案不同**：

| 方案 | 层次 | 效果 |
|---|---|---|
| 按 `kind` 排除 frontmatter | **检索层** | ✗ 误伤崇左 13.1 四条真条件 |
| 含 MUST_FAIL 才保留 hits | **检索层** | ✗ 那四条排 25–28 被字数截断，无收益 |
| **不含后果词的行降级** | **行级（抽取后）** | ✅ 挡得住操作说明，不误伤真条件 |

### ③ 崇左的检索为什么这么差（14%）

废标表 13 行，`refs` 只有 15 个。可能原因：
- 条款切分把长内容合并，`refs` 文本匹配不上
- 崇左结构最乱（前面章节诊断过：缺 qualify 章、前附表在 notice 里）

**没查，记在这。** 全扫把这个问题绕过去了（不依赖 refs 匹配），但如果以后还要用检索，这是必须先查的。

## 七、结论与下一步

### 数据能支持的结论

1. **分片 MapReduce 适合本项目的废标表**：穷举任务、可复现、成本 4–5 次调用 / 6–13 秒
2. **Reduce 只做去重，不做归纳**：去重率 15–16%，必须做；归纳会丢信息
3. **全扫对检索差的文档收益巨大**：崇左 14% → 71%
4. **但全扫不能替代校验**：25% 噪声必须有行级规则兜底

### 还没做的（按优先级）

| 顺序 | 做什么 | 工期 | 预期 |
|---|---|---|---|
| 1 | 全扫接进 `node_feibiao`（替代检索） | 半天 | 废标覆盖率 14–35% → 54–71% |
| 2 | 行级校验（不含后果词的行降级） | 1 小时 | 挡掉 25% 噪声 |
| 3 | 重跑门禁 | 15 分钟 | 看 21 题掉不掉（行数变多可能影响 expect_pages 交集） |
| 4 | 材料表 / 合同表同样处理 | 1 天 | 同上 |
| 5 | 崇左 refs 匹配为什么这么差 | 半天 | 如果还要用检索就得查 |
