# 切分策略

chunk 怎么切。结论先行：**不是「标题 / 条款 / 段落」三选一，是匹配和返回用两个不同的单位。**

## 一、问题：条款切分接入索引后掉分

`TENDER_CHUNK_UNIT=clause` 实测（3 次取多数，`eval/run_regression.py`）：

| | 段落模式（默认） | 条款模式 |
|---|---|---|
| 正例 | 16/18 | **15/18** |
| 负例 | 3/3 | 3/3 |
| ★ 覆盖标记页 | 2 | **0** |
| 掉的题 | — | `cz-format-bid-sheet` |

切分质量本身没问题：抽查 8 条 `X.Y` 全是完整编号条款（20–126 字），条款数 524/487/321，字数中位 62/60/51。

## 二、根因：一个单位干了两件事

检索链路上有个隐含假设：**chunk 既是打分单位，也是喂给模型的上下文单位**。段落模式能凑合，因为 380 字刚好两个角色都合格。条款模式把它拆穿了：

- 打分要小：★/▲ 那类条款只有 20–60 字，作为 chunk 更精确，但 BM25 词频低，`k=6` 的 top-k 里排不进去 → ★ 覆盖归零；
- 喂模型要大：`12.1` 单独一条只有一句话，模型需要看到整个 `第 12 条`（12.1–12.6）才判得准 → 格式章那种表格类条款直接判错。

`k=6` 和写死的 query 常量都是为 380 字段落校准的，切换单位等于换了个物理量，参数必须跟着变——但**先改参数只能补救一部分，正解是把两个角色分开**。

## 三、候选策略

| 策略 | 做法 | 判断 |
|---|---|---|
| **父子切分**（small-to-big / parent-child） | 用条款匹配打分，返回最近的编号祖先给模型 | ✅ 首选。★ 短条款靠自身关键词命中，父级补上下文 |
| **表格行切片**（header-aware） | 一行一个 chunk，表头随行携带 | ✅ 评分表 / 材料清单必须这么做，否则跨页丢行 |
| **按章型选单位**（section-type-aware） | 评标办法走表格行、须知走条款、格式章走表单 | ✅ 成本最低，按章分库的架构天生支持每库不同单位 |
| 固定窗口 + 重叠 | 512 字窗口、128 重叠 | ❌ 无结构长文的解法；有编号的文档切碎只会丢条款 |
| 语义切分（embedding 断点） | 相似度骤降处断 | ❌ 断点对不对没有标准答案，不可评测 |
| 层级摘要（RAPTOR 式） | 多级摘要，检摘要再下钻 | ❌ 答案必须落原文页码，摘要给不出证据 |

## 四、结论：四层，各管一件事

| 层 | 单位 | 用途 |
|---|---|---|
| 匹配 | 条款（最小可判单元） | BM25 / 向量打分 |
| 返回 | 最近的编号祖先 | 给模型的上下文 |
| 表格 | 行 + 表头 | 评分项 / 材料项 |
| 兜底 | 章 | 检索不到时给整章 |

关键：**证据框仍是命中的那一小条，只有上下文取父级。** 框和上下文混在一个粒度里，要么框盖半页，要么模型看不到整条。

## 五、实施设计

### 层级从哪来：书签优先，不是逐块猜

**书签本身就是现成的层级树**（PDF 大纲），比在正文里猜可靠得多：

| 源 | 覆盖率 | 用途 |
|---|---|---|
| PDF 书签 `doc.get_toc()` | beijing 99 条（L1×6/L2×81/L3×12）、chongzuo 51 条（四层）、wenling 仅 7 条 | 骨架：章 → 节 |
| 目录页文本 | 三份里只有 chongzuo 有（p2，点线 + 页码） | 书签缺失时补章级 |
| 章内编号形态 | 全部 | 细级：`X.Y` / `X.Y.Z` |
| x0 缩进 | 北京第二章有 139/184/229 三档（130/84/26 块） | 最后兜底，单独用会误判 |

**书签必须过质量闸**，实测三份文档的书签质量差很多：

- L1 且形如「第X章」→ 章（depth 0）；
- L1 但不是章（`（一）适用范围`、`目 录`，Word 导出的书签常有）→ 降成节（depth 1）；
- 纯数字、少于 3 字、不含汉字 → 丢弃（崇左有 `1`、`9`、`21` 这种条目）；
- 同一页出现多个「第X章」开头的块 → 那是目录页或前附表的章节索引，全部不认。

匹配规则只认「块以书签标题开头」。放开成反向包含会误配：须知正文里提一句「投标文件格式」，就把第七章的书签挂到第 17 页，整章父链全错。

建树用栈：遇深度 d，弹出栈中 `depth >= d` 的，父取栈顶；正文块挂当前栈顶。

北京修完的实测父链：

```
12.1    → 12 投标保证金 (d1) → 第二章 投标人须知 (d0)
11.2.1  → 11.2 投标人的报价… (d2) → 11 投标报价 (d1) → 第二章 投标人须知 (d0)
```

### 上下文要有预算（实测踩过的坑）

第一版把「同编号前缀的整组兄弟」全拼进 context：`12.1` 的上下文就是 12.1–12.6，单条能到 3000 字，`k=6` 合计一万八。结果模型反而抽漏，正例从 15 掉到 **10/18**，掉的正是「最高限价」「有效期」这种需要精确读一条的题。

第二版改滑动窗口（前后各 2 条）回到 12/18，但仍是位置近似、跨议题会串。

第三版才回到本来的设计：**父标题链 + 本条**。`12.1` 的上下文是「第二章 投标人须知 / 12 投标保证金 / 12.1 …」——标题只有十几到几十个字，语义正好是「这一条在讲什么」，字数天然可控。

```
MAX_CONTEXT_CHARS = 1000
```

规律：**上下文的作用是补足语义，不是塞更多字。** 兄弟条款在招标文件里是并列枚举（保证金金额、交纳形式、联合体），拼多了就是拿三件不相干的事挤占注意力。

### 字段与链路

```
ClauseNode.parent_id      ← 父条款 id（None 表示无）
chunk.context             ← 父级 2 层的拼接文本（仅 clause 单位有）
hit.context               ← 检索命中透传
_hit_blob()               ← 用 context 拼提示词；缺省回退 text
Ref.text                  ← 仍是命中条款原文（证据），不是父级
```

`Ref.bbox` 也不变，仍是条款级框。父级只影响模型看到的文字，不影响证据。

### 按章型选单位（第二阶段）

同一份文档里不同章用不同单位，`build_tender_index` 已经按章分库，只需给每章传一个 unit：

| 章 | 单位 | 理由 |
|---|---|---|
| 评标办法 | 表格行 | 一个评分项 = 一行，跨页表要合并 |
| 投标文件格式 | 表格行 / 表单 | 「空位对照」就是找空栏 |
| 投标人须知、资格审查、合同 | 条款 | 条件类文本，编号完整 |
| 采购需求 | 条款 + 表格 | 技术参数常是表格 |

## 六、实验结果（三份样本，3 次取多数）

| 方案 | 正例 | ★ 覆盖页 | 备注 |
|---|---|---|---|
| 段落模式（基线，默认） | **16/18** | 2 | 380 字拼段 |
| 条款 + 无 context | 15/18 | 0 | 掉 `cz-format-bid-sheet` |
| 条款 + 整组兄弟 context（≤3000 字） | **10/18** | 0 | 提示词爆炸，掉 `bj-cap`/`wl-cap`/`wl-validity` |
| 条款 + 滑动窗口 context（前后各 2 条，≤1000 字） | 12/18 | 0 | 比整组好，仍不够 |
| 条款 + 父标题链（书签建树，≤1000 字） | **13/18** | 1 | 父链正确，但检索参数没跟上 |

**结论：上下文粒度已经调到最优，剩下的差距在检索层。**

- 上下文排序：父标题链（13）> 滑动窗口（12）> 无 context（15，但框不准）> 整组兄弟（10）。兄弟最差，因为它给的是并列枚举而不是父级。
- 但没有任何一种上下文能让条款模式追上段落模式（16）。掉的两题 `cz-format-bid-sheet`、`wl-validity` 都需要「整表/跨条」的信息，`k=6` 是给 380 字段落定的，条款更短，6 条覆盖不到。
- `k=12` 试过两次：都出现「模型连续返回空结构化结果」——加了 8000 字总预算之后仍然偶发（3 次跑里有 1 次崩），不是提示词长度问题，是结构化输出在条目多时不稳。重试已从 3 次提到 5 次，但 k 的取值需要单独一轮调（T4），别在切分轮里顺带调。

## 七、验收

1. clause 模式门禁：**当时**定的线是「≥ 段落基线 16/18」，**实际停在 14/18**（2026-11-24，★ 覆盖反而从 2 升到 3）。这条线基于段落模式的覆盖能力，条款更短、单条信息更少，追不上；现行验收看 `docs/规则/回归门禁.md` 的「当前基线」，判据是「不继续下降 + ★ 覆盖不降」。
2. 抽查 3 条命中：`Ref.text` 是条款原文、`context` 含相邻条款（命 12.1 时能看到 12.2/12.3）。
3. 单条 context ≤ 1000 字（超了会挤占注意力，实测正例从 15 掉到 10）。
4. 达不到第 1 条就继续默认 paragraph，别为了架构好看让分数掉。
